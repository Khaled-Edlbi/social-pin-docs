# ✅ Rings · Backend Delivery

**Feature:** [[F-11 Rings]] · **Status:** Done · **Integration guide:** [[BI-08 Rings Backend Integration]] · **Requirements:** [[FR-11 Rings Frontend Requirements]] · **QA:** [[QB-12 Rings QA Backend]]

What the backend shipped for this feature and how it works, as on backend `main` `e483d49`.

## Endpoints, tables and code

**Endpoints**

- `GET /rings`
- `GET /rings/shared-with-me` (one row per person)
- `GET /rings/shared-with-me/count`
- `POST /rings`
- `GET /rings/:id`
- `PATCH /rings/:id`
- `POST /rings/:id/default` (refuses a temporary Ring)
- `POST /rings/:id/copy`
- `POST /rings/:id/disposition`
- `DELETE /rings/:id`

**Tables / models:** `Ring`, `RingTemplate`. Migration `20261105120000_ring_settings` adds six columns to `rings` (`purpose`, `join_policy`, `require_approval`, `members_can_see_each_other`, `members_can_invite`, `members_can_save_attachments`) and the enum `RING_JOIN_POLICY` (`ANYONE_WHO_SCANS`, `CODE_OR_INVITATION`, `INVITATION_ONLY`). Additive; every existing Ring gets the private defaults ([[Database & Migrations]]).

**Code:** `src/modules/ring/` (`ring.service.ts`, `ring.controller.ts`, `ring.query-builder.service.ts`, `dto/copy-ring.dto.ts`, `dto/search-shared-with-me.dto.ts`, `entities/shared-with-me-person.entity.ts`), `src/modules/ring-access/ring-access.service.ts` (`resolvePeopleSharingWith`), and two helpers in `src/modules/ring-profile/ring-profile.service.ts` (`copyProjection`, `cardsForRings`).

## How it works

`RingService` owns the lifecycle; every permission question goes to `RingAccessService`. `POST /rings` defaults the type to `PERSONAL`, rejects `EVENT` / `MINI_EVENT` / `MEETING` (400 `E_RING_01`, their own flows create them with a context behind them), checks the per-owner name clash and inserts in one transaction (409 `E_RING_01`), requires `parentRingId` and `profileId` to be the caller's own (400 `E_RING_06` / `E_RING_08`) and falls back to the default profile. `GET /rings` is scoped by `RingQueryBuilderService` (`name`, `type`, `status`, `isTemporary`; `deletedAt: null` in `defaultQuery`), default first then newest. `GET /rings` and `GET /rings/:id` also carry each Ring's live `memberCount` ([[BD-03 Counts Backend Delivery]]). `PATCH /rings/:id` passes through `assertCanAdminister(…, 'CONTENT_MANAGER')`, which ignores the Ring's expiry so an expired Ring stays editable. `POST /rings/:id/default` demotes then promotes in one transaction (partial unique index: one default per owner). `POST /rings/:id/disposition` runs `UNDECIDED → KEEP | MERGE | AUTO_DELETE`, and only on a temporary Ring whose window has ended (`isTemporary`, not the default, `expiresAt` set and not after now): anything else is 409 `E_RING_10` before anything is written, and `UNDECIDED` is a 400; a decision can still be changed while the Ring is temporary (AUTO_DELETE, then KEEP). `KEEP` clears the expiry and the temporary flag; `MERGE` needs another Ring of the same owner (400 `E_RING_07`), upserts every active member into the target with their window (an expired row there is reactivated rather than skipped), marks the source rows `REMOVED` and the Ring `ARCHIVED` with `mergedIntoRingId`; `AUTO_DELETE` archives and sets `expiresAt` to now, leaving the purge to the retention job. `DELETE /rings/:id` is a soft delete and refuses the default (409 `E_RING_04`), because a scanned QR needs one Ring that resolves. Set-default, copy, disposition and delete are **owner-only**: anyone else, a delegated admin included, gets 404 `E_RING_02`. The backend never writes `RING_STATUS.EXPIRED`; expiry is evaluated live from the timestamps.

**The six settings (S9, [[D-04 Ring settings at launch and their defaults]]).** Stored as typed columns on the Ring (ND-04's option B), each with its private default: `purpose` (who it's for, up to 140 characters, `null`), `joinPolicy` (`CODE_OR_INVITATION`), `requireApproval` (`true`), `membersCanSeeEachOther`, `membersCanInvite`, `membersCanSaveAttachments` (all `false`). `POST /rings` and `PATCH /rings/:id` take any of them (left out, the column default applies; `purpose: null` clears it); `RingEntity` returns all six on `GET /rings`, `GET /rings/:id` and every owner write. The owner and a `CONTENT_MANAGER`-level admin may change them, through the same `assertCanAdminister` as the rest of `PATCH`. What is enforced today, in `RingAccessService` ([[S-15 Ring Access Engine Story|Ring Access Engine · S8]]): **"members can see each other"** gates the member count on Shared with me (below); there is no member-facing roster route at all, so off means no roster anywhere. **Enforced by [[F-17 Ring Invitations & Join]] since `main` `1c460b0`** ([[BD-17 Ring Invitations & Join Backend Delivery]]): `joinPolicy` (a join code works under `ANYONE_WHO_SCANS` and `CODE_OR_INVITATION`, never `INVITATION_ONLY`; an invitation works under all three), `requireApproval` (a code makes a join request the owner approves, else it joins at once), `membersCanInvite` (a live member may invite only while it is on). **Stored, enforced when the flow ships:** `membersCanSaveAttachments` (no save-attachment flow exists; a member who can see an attachment on the card can open it through its signed link, which is viewing, not saving).

**Validation at the edge.** Every boolean (`isTemporary` on `GET /rings`, `isTemporary` and the four boolean settings on `POST` / `PATCH /rings`) goes through the shared `@ToBoolean()` (`src/common/decorators/to-boolean.decorator.ts`): `true` / `"true"` and `false` / `"false"` are read as sent and any other value is a 400; before it, the global pipe's implicit conversion read every string as `true` ([[B-13 The string false is read as true on Ring filters and settings]]). `UpdateRingDto` is `PartialType(CreateRingDto, { skipNullProperties: false })`: `null` passes only on the fields that clear (`purpose`, `colorHex`, `style`, `startsAt`, `expiresAt`, `parentRingId`, which detaches the parent) and is a 400 on every other field, never a 500 from the database ([[B-14 PATCH a Ring with null on a required field answers 500]]). `colorHex` matches `^#[0-9A-Fa-f]{6}$` and `purpose` is 1–140 characters after trim, or `null`, on create, edit and copy ([[B-16 Ring colour and purpose accept values the contract refuses]]).

**Copy a Ring (S4, [[D-05 Inherit per field, copy without members]]).** `POST /rings/:id/copy { name, colorHex?, style?, purpose? }`, owner-only (404 `E_RING_02`), one transaction: the name clash (409 `E_RING_01`), a new Ring with the source's `profileId`, colour, style, purpose and the other five settings (each of the first three overridable in the body), then `RingProfileService.copyProjection`, which copies the projection row (name and bio overrides, photo, theme, the sensitive-field switches) and switches on **the same library items** the source shows ([[D-03 Links entered once, switched on or off per Ring]]): each link and info block switch is copied by `linkId` / `infoBlockId` with its own order and `isVisible`, pointing at the owner's existing `LibraryLink` / `LibraryInfoBlock` rows, so nothing in the library is duplicated and an edit to a library item shows on both Rings. Widgets and attachments are copied as new rows with their own `isVisible`. **Never copied:** members, admins, QR and NFC tokens, the window. The copy is always a permanent `PERSONAL` Ring, `ACTIVE`, not the default; after the copy the two Rings are independent. A source with no projection yet copies none (the copy's is created on its first edit, as for any Ring).

**Refuse a temporary default (S7).** `POST /rings/:id/default` on an `isTemporary` Ring answers 409 `E_RING_09` before demoting anything; `PATCH /rings/:id { isTemporary: true }` on the current default answers the same, so the rule cannot be undone by an edit. Ownership is checked first (404 `E_RING_02`).

**Shared with me per person ([[S-15 Ring Access Engine Story|Ring Access Engine · S1]], [[D-14 Shared with me lists people, never the Ring]], [[D-15 Several Rings per connection, remove or disconnect]], [[D-18 Ring names shown when joined knowingly]]).** `GET /rings/shared-with-me` lists **people**. `RingAccessService.resolvePeopleSharingWith` reads the caller's live memberships in Rings `sharedWithFilter` allows (the Ring live, the membership live, no block either way, never the caller's own), keeps per owner the oldest membership the caller **joined knowingly**, else the one created first (the Ring the caller was put in first, D-15; the knowing one wins since `main` `1c460b0`, so S-33 S2's "the owner is on Shared with me with the Ring's name" holds for someone already placed in another of their Rings), and orders people by that membership, newest first. Each row's `expiresAt` is the earlier of that Ring's and the membership's end. The row carries the Ring's name only where `isRingNamedToMember` allows it (D-18): when `RingMember.origin` is not `PLACED`, i.e. the caller accepted an invitation (`INVITATION`), joined with a code (`JOIN_CODE`) or had a join request approved (`JOIN_REQUEST`) ([[BD-17 Ring Invitations & Join Backend Delivery]]). An owner or admin add, a connection accept and a reassign are `PLACED` and never named. A member count is computed only on a named row whose Ring has `membersCanSeeEachOther` on. `RingService` pages that list (in memory: the caller's own memberships grouped by person), and puts the person's card on each row through `RingProfileService.cardsForRings`, which renders the same `toView` as every `/views` route (Pin name, the Ring's name override else the profile name, the signed photo link); a Ring with no projection yet renders as an empty one would (its profile, no photo). `meta.total` is the number of people, so it equals `GET /rings/shared-with-me/count`, which still uses `countPeopleSharingWith` on the same `sharedWithFilter`. The route takes **pagination only**: a filter on a Ring's `name`, `type`, `status` or `isTemporary` is a 400, because it would let a member test which Ring they are in.

### What exists

- Filters on `GET /rings`: `name`, `type`, `status`, `isTemporary`. One default Ring per owner (partial unique index).
- `EVENT`, `MINI_EVENT` and `MEETING` Rings are rejected on `POST /rings`; their own flows create them.
- `POST /rings/:id/disposition` runs `UNDECIDED → KEEP | MERGE | AUTO_DELETE` on a temporary Ring whose window has ended, and refuses any other Ring, the default included (409 `E_RING_10`); `AUTO_DELETE` archives and flags rather than deleting.
- Owner editing uses `assertCanAdminister`, which ignores expiry so an expired Ring stays editable; set-default, copy, disposition and delete are owner-only.
- Member counts per owned Ring (`memberCount`) on the list and the detail, and the Shared-with-me people count: see [[BD-03 Counts Backend Delivery]].
- `GET /rings/shared-with-me` honours blocks both ways, through `RingAccessService.sharedWithFilter` (since `main` `f186ba1`).
- The six D-04 settings with their defaults, read and written by the owner; the purpose for the s16 row (since `main` `12172c6`).
- `POST /rings/:id/copy`, without members (D-05), switching on the same library items (D-03).
- A temporary Ring cannot be the default (409 `E_RING_09`).
- Booleans read as sent (`"false"` is false, anything but true / false is 400), `null` on a PATCH only where it clears, `colorHex` as `#RRGGBB`, `purpose` 1–140 after trim (since `main` `e483d49`).
- Shared with me is one row per person, with their card and the `ringId` that opens it; no Ring colour, type, settings or owner id; Ring filters refused (400).

### Gaps

- `membersCanSaveAttachments` is saved but enforced only when a save flow exists.
- Who may change which setting: today the owner and a `CONTENT_MANAGER`-level admin may change all six; [[S-31 Delegated Admins Story]]'s levels (member-managers change the joining settings and the purpose) come with [[F-16 Delegated Admins]].
- Whether a copied Ring's fields keep inheriting the main profile (D-05, *Still open*): the copy takes the source's projection values as they are; per-field inheritance is [[F-10 Ring Projection]]'s.
- `POST /rings` creates no projection row (the owner's first `GET /rings/:ringId/projection` does); since `main` `e483d49` the viewer paths render such a Ring as the empty perspective, so `GET /views/ring/:ringId` no longer answers 404 for it ([[B-17 A new Ring answers 404 to its own owner until its projection is opened]], `90fc7b3`).
- The sweeper that materialises `RING_STATUS.EXPIRED` and purges `AUTO_DELETE` Rings is not written. See [[F-31 Cleanup Jobs]].
