## How it works

`RingService` owns the lifecycle; every permission question goes to `RingAccessService`. `POST /rings` defaults the type to `PERSONAL`, rejects `EVENT` / `MINI_EVENT` / `MEETING` (400 `E_RING_01`, their own flows create them with a context behind them), checks the per-owner name clash and inserts in one transaction (409 `E_RING_01`), requires `parentRingId` and `profileId` to be the caller's own (400 `E_RING_06` / `E_RING_08`) and falls back to the default profile. `GET /rings` is scoped by `RingQueryBuilderService` (`name`, `type`, `status`, `isTemporary`; `deletedAt: null` in `defaultQuery`), default first then newest. `GET /rings` and `GET /rings/:id` also carry each Ring's live `memberCount` ([[BD-03 Counts Backend Delivery]]). `PATCH /rings/:id` passes through `assertCanAdminister(…, 'CONTENT_MANAGER')`, which ignores the Ring's expiry so an expired Ring stays editable. `POST /rings/:id/default` demotes then promotes in one transaction (partial unique index: one default per owner). `POST /rings/:id/disposition` runs `UNDECIDED → KEEP | MERGE | AUTO_DELETE`: `KEEP` clears the expiry and the temporary flag; `MERGE` needs another Ring of the same owner (400 `E_RING_07`), upserts every active member into the target with their window (an expired row there is reactivated rather than skipped), marks the source rows `REMOVED` and the Ring `ARCHIVED` with `mergedIntoRingId`; `AUTO_DELETE` archives and sets `expiresAt` to now, leaving the purge to the retention job. `DELETE /rings/:id` is a soft delete and refuses the default (409 `E_RING_04`), because a scanned QR needs one Ring that resolves. Set-default, copy, disposition and delete are **owner-only**: anyone else, a delegated admin included, gets 404 `E_RING_02`. The backend never writes `RING_STATUS.EXPIRED`; expiry is evaluated live from the timestamps.

**⏳ branch · the six settings (S9, [[D-04 Ring settings at launch and their defaults]]).** Stored as typed columns on the Ring (ND-04's option B), each with its private default: `purpose` (who it's for, up to 140 characters, `null`), `joinPolicy` (`CODE_OR_INVITATION`), `requireApproval` (`true`), `membersCanSeeEachOther`, `membersCanInvite`, `membersCanSaveAttachments` (all `false`). `POST /rings` and `PATCH /rings/:id` take any of them (left out, the column default applies; `purpose: null` clears it); `RingEntity` returns all six on `GET /rings`, `GET /rings/:id` and every owner write. The owner and a `CONTENT_MANAGER`-level admin may change them, through the same `assertCanAdminister` as the rest of `PATCH`. What is enforced today, in `RingAccessService` ([[S-15 Ring Access Engine Story|Ring Access Engine · S8]]): **"members can see each other"** gates the member count on Shared with me (below); there is no member-facing roster route at all, so off means no roster anywhere. **Stored, enforced when the flow ships:** `joinPolicy` and `requireApproval` (invitations and join codes, [[F-17 Ring Invitations & Join]]; until then nobody joins a Ring by themselves), `membersCanInvite` (member invitations, F-17), `membersCanSaveAttachments` (no save-attachment flow exists; a member who can see an attachment on the card can open it through its signed link, which is viewing, not saving).

**⏳ branch · copy a Ring (S4, [[D-05 Inherit per field, copy without members]]).** `POST /rings/:id/copy { name, colorHex?, style?, purpose? }`, owner-only (404 `E_RING_02`), one transaction: the name clash (409 `E_RING_01`), a new Ring with the source's `profileId`, colour, style, purpose and the other five settings (each of the first three overridable in the body), then `RingProfileService.copyProjection`, which copies the projection row (name and bio overrides, photo, theme, the sensitive-field switches) and switches on **the same library items** the source shows ([[D-03 Links entered once, switched on or off per Ring]]): each link and info block switch is copied by `linkId` / `infoBlockId` with its own order and `isVisible`, pointing at the owner's existing `LibraryLink` / `LibraryInfoBlock` rows, so nothing in the library is duplicated and an edit to a library item shows on both Rings. Widgets and attachments are copied as new rows with their own `isVisible`. **Never copied:** members, admins, QR and NFC tokens, the window. The copy is always a permanent `PERSONAL` Ring, `ACTIVE`, not the default; after the copy the two Rings are independent. A source with no projection yet copies none (the copy's is created on its first edit, as for any Ring).

**⏳ branch · refuse a temporary default (S7).** `POST /rings/:id/default` on an `isTemporary` Ring answers 409 `E_RING_09` before demoting anything; `PATCH /rings/:id { isTemporary: true }` on the current default answers the same, so the rule cannot be undone by an edit. Ownership is checked first (404 `E_RING_02`).

**⏳ branch · Shared with me per person ([[S-15 Ring Access Engine Story|Ring Access Engine · S1]], [[D-14 Shared with me lists people, never the Ring]], [[D-15 Several Rings per connection, remove or disconnect]], [[D-18 Ring names shown when joined knowingly]]).** `GET /rings/shared-with-me` lists **people**. `RingAccessService.resolvePeopleSharingWith` reads the caller's live memberships in Rings `sharedWithFilter` allows (the Ring live, the membership live, no block either way, never the caller's own), keeps per owner the membership created first (the Ring the caller was put in first, D-15), and orders people by that membership, newest first. Each row's `expiresAt` is the earlier of that Ring's and the membership's end. The row may carry the Ring's name only where `isRingNamedToMember` allows it (D-18), which is **never today**: a membership does not record how it was made ([[F-09 Ring Members]]), and every membership that exists was made by the owner or an admin. A member count is computed only on a named row whose Ring has `membersCanSeeEachOther` on, so it is also never today. `RingService` pages that list (in memory: the caller's own memberships grouped by person), and puts the person's card on each row through `RingProfileService.cardsForRings`, which renders the same `toView` as every `/views` route (Pin name, the Ring's name override else the profile name, the signed photo link); a Ring with no projection yet renders as an empty one would (its profile, no photo). `meta.total` is the number of people, so it equals `GET /rings/shared-with-me/count`, which still uses `countPeopleSharingWith` on the same `sharedWithFilter`. The route takes **pagination only**: a filter on a Ring's `name`, `type`, `status` or `isTemporary` is a 400, because it would let a member test which Ring they are in.

### What exists

- Filters on `GET /rings`: `name`, `type`, `status`, `isTemporary`. One default Ring per owner (partial unique index).
- `EVENT`, `MINI_EVENT` and `MEETING` Rings are rejected on `POST /rings`; their own flows create them.
- `POST /rings/:id/disposition` runs `UNDECIDED → KEEP | MERGE | AUTO_DELETE`; `AUTO_DELETE` archives and flags rather than deleting.
- Owner editing uses `assertCanAdminister`, which ignores expiry so an expired Ring stays editable; set-default, copy, disposition and delete are owner-only.
- Member counts per owned Ring (`memberCount`) on the list and the detail, and the Shared-with-me people count: see [[BD-03 Counts Backend Delivery]].
- `GET /rings/shared-with-me` honours blocks both ways, through `RingAccessService.sharedWithFilter` (since `main` `f186ba1`).
- ⏳ branch: the six D-04 settings with their defaults, read and written by the owner; the purpose for the s16 row.
- ⏳ branch: `POST /rings/:id/copy`, without members (D-05), switching on the same library items (D-03).
- ⏳ branch: a temporary Ring cannot be the default (409 `E_RING_09`).
- ⏳ branch: Shared with me is one row per person, with their card and the `ringId` that opens it; no Ring colour, type, settings or owner id; Ring filters refused.

### Gaps

- On `main` until the merge: `GET /rings/shared-with-me` still returns the Ring itself (name, colour, type) to every member; the settings, copy and the temporary-default refusal do not exist.
- A Ring's name and a member count on Shared with me wait for memberships to record how they were made ([[F-09 Ring Members]], D-18); until then every row is the person.
- `joinPolicy`, `requireApproval`, `membersCanInvite` are saved but enforced only when invitations and codes ship ([[F-17 Ring Invitations & Join]]); `membersCanSaveAttachments` when a save flow exists.
- Who may change which setting: today the owner and a `CONTENT_MANAGER`-level admin may change all six; [[S-31 Delegated Admins Story]]'s levels (member-managers change the joining settings and the purpose) come with [[F-16 Delegated Admins]].
- Whether a copied Ring's fields keep inheriting the main profile (D-05, *Still open*): the copy takes the source's projection values as they are; per-field inheritance is [[F-10 Ring Projection]]'s.
- `POST /rings` creates no projection; `GET /views/ring/:ringId` answers 404 for a shared Ring whose owner never opened "what it shows", while its Shared-with-me row still renders the person from the profile.
- The sweeper that materialises `RING_STATUS.EXPIRED` and purges `AUTO_DELETE` Rings is not written. See [[F-31 Cleanup Jobs]].
