# ✅ Discover Hub & Search · Backend Delivery

**Feature:** [[F-19 Discover Hub & Search]] · **Status:** Done · **Integration guide:** [[BI-19 Discover Hub & Search Backend Integration]] · **Requirements:** [[FR-19 Discover Hub & Search Frontend Requirements]] (approved 2026-11-23) · **QA:** [[QB-18 Discover Hub & Search QA Backend]]

What the backend shipped for this feature and how it works. Two scopes: the exact-name lookup ([[D-37 Discover opens a Pin by its exact Pin name in the MVP|D-37]], on `main` since `3cef5d7`, nothing of this feature's own) and the search by part of a Pin name ([[D-41 Discover searches people by part of their Pin name|D-41]], [[S-42 Discover Hub & Search Story|S-42]] S2, S4, S5), built on backend branch `BD-19/search/pin-name-search` (`c5bc838`) and **merged to `main` on 2026-11-23** (a fast-forward, no merge commit: GitHub's `main`, `github.com/Khaled-Edlbi/social-pin`, and the GitLab remote's `main`, `gitlab.com/MolhamStein/social-pin-backend`, both end at `c5bc838` since the push of 2026-11-23).

### How it works

1. **The query.** `q` is trimmed, a leading `!` or `@` dropped, then lowercased, the same normalisation as `pin_name_normalized`. Under 3 letters: 400 `E_SEARCH_01` before any lookup. Then the per-person limit counts the search: 30 in a sliding minute, over it 429 `E_SEARCH_02`. Only a search that runs is counted: one refused for being under 3 letters is refused before the count, and one refused with 429 adds nothing to the window, so the window empties 60 seconds after the searches that did run (QB-18 B53, B54).
2. **Who may be found** (S5, Q3). One base filter: default profiles only, live profile, `ACTIVE` undeleted account, never the searcher, never anyone in a block with the searcher in either direction (`user_blocks`, both ways). On top of it, the switch: a person with `findable_by_pin_name` off is found only by people already in one of their Rings. "In one of their Rings" is `RingAccessService.resolvePeopleSharingWith(viewer, now)`, the engine's answer against `now` (both windows live, blocked pairs left out), so the switch and a removal from a Ring apply to the next search at once; nothing is cached.
3. **Order and pages** (Q1, Q2). Three groups over the base filter, counted and paged as one list: (1) the exact normalised name, if its owner may be found; (2) people who have the searcher in a Ring, letters anywhere; (3) everyone else with the switch on, letters anywhere. A→Z by normalised Pin name inside a group, then by id, so pages are stable. `meta.total` is the sum of the three counts; a page can straddle a group boundary.
4. **Each row.** From the default profile: `pinName` (as the owner spelt it), `accountName` = `fullName` (nullable), `avatarUrl` = the signed link to `avatarFileId` (15 minutes, [[D-16 Files load from signed links that expire in 15 minutes|D-16]]; null without a photo). The same for every searcher: nothing from any Ring projection, so a list never says which Ring the searcher is in. `relationship` from two queries for the page: a live `connections` row → `CONNECTED`; else the pair's one pending, unexpired `connection_requests` row ([[D-24 One pending request per pair|D-24]]) → `ASKED_ME` (theirs) or `REQUESTED` (mine), with `requestId`; else `NONE`. `canOpenCard` is true exactly for group 2's people (the engine's set), whatever the relationship.
5. **The switch.** `findableByPinName` on `AccountEntity` (`GET /users/me`), set with `PATCH /users/me` like email and phone; `true` for every existing account by the migration's default. Not exposed on the admin panel's `AdminUserEntity`.

### What exists

- The search above, the result row, the limit and the switch: on `main` since the merge of `BD-19/search/pin-name-search` (`c5bc838`, 2026-11-23), with specs for the query rules, the three groups and their paging, the filters, the four relationships, `canOpenCard`, the signed photo and the absence of any id on the wire.
- Resolving one exact Pin name: `GET /views/pin/:pinName` answers the view of what that person shares with the viewer, with `pinName` and `displayName` (which may be `null`), no Ring id and no user id. It is View As & Pin Views' route; how to call it is [[BI-09 View As & Pin Views Backend Integration]]. The lookup is not a membership oracle: unknown, not shared and blocked all answer the same 404 `E_RING_ACCESS_01`. A deleted account does not yet: on `main` a member of one of its Rings still gets 200 ([[B-28 A deleted account's card still opens for a member of its Ring|B-28]], *Gaps*).
- The viewer's own Pin name and photo: `pinName`, `avatarUrl` on `GET /profiles`.
- Accept from a result: `POST /connections/requests/:id/accept` with the row's `requestId` ([[BD-14 Connections Backend Delivery]], [[BI-16 Connections Backend Integration]]).
- Connect from a result, **only for a person whose card the searcher can already open** (`canOpenCard` true): `POST /connections/requests` `{ pinName }`. For anyone else it is refused (*Gaps*).

### Gaps

- **Connect does not work from a not-connected row** (S-42 S2, QB-18 B43). `POST /connections/requests` `{ pinName }` answers 404 `E_RING_ACCESS_01` unless the requester can already open that person's card: Connections accepts a request by Pin name only then, and a stranger connects by scanned code ([[BI-16 Connections Backend Integration]]). So the row the search exists for, a stranger with `relationship` `NONE` and `canOpenCard` false, has a Connect that cannot be sent. Nothing was built for it: whether a person found by search may be asked by Pin name is a product decision (the story's and Connections'), and this note is Partial until it is taken.
- **A deleted account's card still opens for a member of its Ring** ([[B-28 A deleted account's card still opens for a member of its Ring|B-28]], QB-18 B7, B14): `GET /views/pin/:pinName` answers 200 on `main`. Fixed on backend branch `B-28/ring-access/deleted-owner-not-shared` (`9463472`, not merged): the access engine's live-Ring filter now also asks for an owner whose account is not deleted, so the resolve, the perspectives, Shared with me and `canOpenCard` all answer as for a name nobody has. The search itself already hides a deleted account.
- **`PATCH /users/me` saves a non-boolean `findableByPinName`** ([[B-29 The find-me switch reads the string false as true|B-29]], QB-18 B61): `"false"` and `"no"` are stored as true on `main`. Fixed on backend branch `B-29/user/findable-switch-boolean` (`812d6a4`, not merged): `true`, `false`, `"true"` and `"false"` are read as sent, anything else answers 400. A real boolean, which is what the app sends, is saved correctly today.

- **Deploy the migration.** `20261123120000_findable_by_pin_name` is one additive column; `pnpm prisma:deploy` on each environment before the search is called there (`deployedTo` says where it runs).- **The limit is per process.** `SlidingWindowLimiter` keeps the window in memory, as the badge scanner's limit does: one instance, one count; behind several instances the effective limit multiplies. A shared store is the fix when the API scales out (the same gap as [[BD-18 Badge & QR Backend Delivery]]).
- **A connected person who shares nothing** (D-29, "No access") reads `CONNECTED` with `canOpenCard: false`: the app shows the Connected row and the tap does nothing, as FR-19 says for a row that cannot open.
- **A request of mine that was declined or expired** reads `NONE` here (Connect again), where `GET /connections/relationship` says `DECLINED` / `EXPIRED` for 30 days. The search shows a button, not a history.
- **Verified by QA, not by an e2e suite:** [[QB-18 Discover Hub & Search QA Backend]] ran all 63 rows on `main @ c5bc838` on 2026-11-23, 59 as expected; the four that failed are the three gaps above. The repo has no e2e spec for the search.
- `avatarUrl` is a path, `/api/v1/files/content/<token>`, not an absolute link: the client puts its API origin in front, as for every signed file link.
- The resolve route does not validate the name's format: a malformed name answers the same 404, never a 400.
- Recent searches: not a gap. They stay on the phone, per user, with no server store (S-42 S3).
- Later (D-37), not built: Gemma (S6), import contacts (S7, phone book match by hashed email / phone), and knowing a Pin name is a business's.
