# Social Pin · Docs vault — rules for anyone (or any agent) editing it

This repository is the documentation vault for Social Pin: the backend
(`github.com/Khaled-Edlbi/social-pin`), the frontend and the product share it.
It is plain Markdown with wikilinks and YAML frontmatter; it also reads on
GitHub. Start at `Home.md`. **The full rules are `rules/Agent Rules.md`**;
this file is the short form and defers to it.

## What lives where

The repository holds two things: the **docs system** at the root (`rules/`, `templates/`, `scripts/`, `tree/`, `.claude/`, `.github/`, `docs.config.json`), which would serve any project, and **the product's docs** in `social-pin/` (`projectDir` in `docs.config.json`). Every card folder named in these rules (`modules/`, `bugs/`, `needs-decisions/`, `decisions/`, `business/`, `frontend/`, `backend/`, `design/`, `Card Index.md`) is inside `social-pin/`: `modules/…` means `social-pin/modules/…`. Wikilinks go by note name and never carry the folder.

| Folder | One note per | Template |
|---|---|---|

| `rules/` | the rules every layer follows: `Workflow`, `Agent Rules`, `Docs Tree`; the agents, one note per role that **is** its prompt: `Agent Protocol` (shared), `Owner Agent`, `PM Agent`, `Backend Agent`, `Frontend Agent`, `QA Agent` | — |

`docs.config.json` declares the layers, their kinds, statuses, the hand-off
flow, the default blocks, the card-code prefixes, the modules and the agents (who writes what). `Card Index.md`, `tree/cards.json`, `tree/tree.json` and `tree/tree.md` are **generated**:
never edit them by hand.

## Read the tree first, then only what `--impact` lists

`tree/tree.json` is the whole vault as one object (nodes, edges, concepts). Read
it before walking folders. Before creating or changing any card, run
`node scripts/build-tree.mjs --impact "<note | card code | feature id | endpoint | E_CODE>"`
and read what it returns: the same feature's notes, the directly linked notes,
the two-hop notes only when the change crosses a feature boundary. To turn the
words a person uses ("the speed search", "the rings module") into cards and ids:
`node scripts/build-tree.mjs --find "<words>"`. How to read the page and the
JSON: `rules/Docs Tree.md`. How an agent takes a request (resolve, align in
one question, act in scope, finish): `rules/Agent Protocol.md`.

## The workflow this vault enforces

`rules/Workflow.md` is the sequence, `rules/Agent Rules.md` the rules; the short form:

1. **One story per feature, one flow** (since 2026-10-27): every piece of work is a part of the feature's story (`### S7 · …`) before code is written; there are no tasks (`type: task` and `--scaffold task` are build errors), and a feature whose notes are already done takes new work as `pending` entries on them (Partial).
2. The branch in every **code** repo is named after the feature: `<module>/<F-NN>/<what-you-do>` (e.g. `ring/F-11/member-count`). In the vault, every agent's branch is named after the card, as deep as it sits: `tickets/<agent>/<M-NN>-<module-id>/<F-NN>-<feature-id>/<card>-<what>` for the cards that ask for or plan work (story, Frontend Requirements, needs-decision, bug), `docs/<agent>/…` for the archive (delivery, integration and QA notes, decision cards, module and feature cards), `docs/<agent>/project/…` for the rules; `node scripts/build-tree.mjs --branch <agent> <card> [<what>]` prints the name (`rules/Workflow.md` §2, `branches` in `docs.config.json`).
3. Each layer writes **its own notes only**, created once per feature with `node scripts/build-tree.mjs --scaffold <kind> <feature-id>` (a feature: `--scaffold feature <module-id> "<Name>"`): frontend requirements before backend work; backend delivery + integration when the API ships; frontend delivery when the screens ship; QA notes (artefacts, never test code) when checks run. The feature's notes hold all of its work; the module note is the sum of its features.
4. Every card in the flow is blocked by default until the card before it is handed off (story and requirements at `approved`, the rest at done; a requirements list goes `draft → ready → approved`: the frontend sets 📨 `ready` when it is complete, the backend approves it or sends it back to `draft`, and `ready` unblocks nothing); a note's `blockedBy` overrides. A card that **needs a decision** gets a decision card under it (`--scaffold needs-decision "<card>" "<title>"`: what has to be decided, notes, who decides) and is Blocked · ND-NN until that card is `decided`, then returns to its own status by itself; never type `blocked` on the card for this. Every note declares `depends` / `affects` / `related` (and `blockedBy` when blocked, by any layer) in frontmatter; after the change, `--impact` again and update or flag (`> ⚠ Affected by [[<the card you changed>]] (date): …`) every note it lists that you do not own.
5. `node scripts/build-tree.mjs` is run and the generated files are committed with the notes. CI runs `--check` on every pull request and fails on errors or drift.

## Conventions

- Frontmatter per note type: structural `type: module | feature | bug | needs-decision | decision | project` and the kind ids from `docs.config.json` (`story`, `frontend-requirements`, `backend-delivery`, `backend-integration`, `frontend-delivery`, `qa-backend`, `qa-frontend`). Statuses: bug `todo | needs-info | blocked | in-progress | done`, needs-decision card `draft | open` (shown ✅ Fulfilled, computed, once its decision card is decided), decision card `draft | decided`; each kind's statuses, *done* set and *handoff* set are in the config. A feature's, a module's and the project's status is **computed**: Done only when every card under it is done, Partial when the cards are done but carry notes, In progress while any card is open, Blocked · ND-NN while a decision raised on the feature itself is open. A done layer note or bug with a `pending: ["[[Note]]: what", "@who: what"]` list is **Partial** until the list is cleared. A **bug** takes the bug statuses and says how it ended in `resolution: fixed | by-design | duplicate | cannot-reproduce | wont-fix` (`resolutions` in the config, tag `resolution/<id>`, the PM's and QA's to set): the outcome, never instead of the status, and a warning when a bug is `done` without one. Tags mirror them (`bug/blocked`, `story/approved`, `qa-backend/passing`, `module/<id>`, `layer/<id>`; a feature carries no status tag). Keep frontmatter flat: scalars, quoted strings and inline `[a, b]` lists only; the build script parses nothing else.
- **Priority and deadline on every card.** `priority: critical | high | medium | low` (the enum is `priorities` in `docs.config.json`; the old `P0`–`P3` are aliases the build still reads with a warning; the tag mirrors it, `priority/high`) and `deadline: YYYY-MM-DD`, both optional. A layer note or a bug without its own inherits its feature's (`inherits` in `tree/tree.json` names the source). The tree draws a **flag** in the level's colour and a **clock** coloured by how close the deadline is: the last `deadlines.windowDays` (3) before it split evenly over the zones, green *on track* → yellow *due soon* → red *last day*, a 💀 once the day is over. The colour is computed when the page is viewed, never written into a generated file.
- **Stage, release, environments.** The project's `stage: concept | prototype | mvp | beta | live | sunset` is typed by the owner in `business/Project Overview.md`, never computed, and sits beside the computed status; a feature's `release: mvp | v1 | later` (owner, feature cards only, inherited below) feeds the project card's release progress; `deployedTo: [dev, staging, prod]` on Backend and Frontend Delivery notes says where it runs. Enums in `docs.config.json` (`stages`, `releases`, `environments`); release and stage are the owner's alone, and the guard refuses either line from any other agent (`agents.reservedFields`); the rule is `rules/Agent Rules.md` §4.
- Headings carry the status emoji: ✅ done · 🟡 partial / in progress · ⬜ todo · 🖼️ frontend only · 🔌 backend integration · 🧪 QA · ❓ decision. Story and requirements notes carry no emoji; their status is the chip in the tree.
- **Card codes.** Every card (one Markdown file in the tree) has one unique code, `<prefix>-<number>`, listed in `Card Index.md` and kept in `tree/cards.json`: a bug's, a needs-decision card's and a decision card's code is its id (`B-01`, `ND-04`, `D-04`: **`ND-` is the question, `D-` its answer, with the same number**); every other card got the next free number for its kind's prefix (`M` module, `F` feature, `S` story, `FR` frontend requirements, `BD` backend delivery, `BI` backend integration, `FD` frontend delivery, `QB` QA backend, `QF` QA frontend, `B` bug, `P` project note) the first time the build saw it and keeps it. A new card gets the next number, a deleted card's code is retired and never handed out again, and a duplicate, renumbered or wrong-prefix code fails the build. Refer to cards by code as `B-01 | S-01`; `--impact S-01` resolves a code.
- **Every card's file name starts with its code** (since 2026-10-28): `B-01 …`, `ND-01 …`, `D-01 …`, and `M-07 Commerce Module`, `F-27 Payments & Orders`, `S-69 Payments & Orders Story`, `FR-27 Payments & Orders Frontend Requirements`: the code, then the name, the kind word kept; folders carry no code. A card is born with its code: `--scaffold feature` and `--scaffold <kind> <feature-id>` take the next free number and repoint the links written to the card's plain name while it was not written yet. Never type a code into a file name by hand and never rename one; the build warns on a card whose name lacks its code and fails on one whose name carries another. Project notes (`P-NN`: `rules/`, `backend/`, `frontend/`, `business/`) keep their plain names.
- Wikilink by note name, code included: `[[F-11 Rings]]`, `[[BI-08 Rings Backend Integration]]`, `[[S-03 Counts Story|Counts · S6–S10]]` with the full title, `[[B-01 …]]`, `[[ND-01 …]]`, `[[D-01 …]]`; a card not written yet by its plain name (`[[<Feature> Backend Integration]]`) until its scaffold repoints it. Screen ids are the prototype's (`[[Screen Index#s44|s44]]`).
- Dates are `YYYY-MM-DD`. Every card carries `created:`, the day it was made: the scaffold or the template writes it once and nobody changes it (the cards made before the rule got the day git first saw the file). Every note touched gets today's `updated:`. The tree page filters on both.
- Describe things as they **are**. A gap written down is better than a feature described as done. Say "not available yet" and link the story part that covers it.
- Project reference (stack, migrations, contracts) stays in `backend/`, `frontend/`, `business/`; feature behaviour stays in the feature's notes. Never both.
- Never edit `design/Wireframe Brief.md`: it is a verbatim copy.
