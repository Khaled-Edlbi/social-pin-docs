# Agent Rules · who writes what, and how a change stays true

Binding for every person and every agent that edits this vault, from any repository. The backend's `CLAUDE.md` and the frontend's (see [[Frontend Agent Prompt]]) both point here; when they differ from this note, this note wins for anything about documentation.

The repository holds two things: the **docs system** at the root (`rules/`, `templates/`, `scripts/`, `tree/`, `.claude/`, `.github/`, `docs.config.json`), which would serve any project, and **the product's docs** in `social-pin/` (`projectDir` in `docs.config.json`). Every card folder named in these rules (`modules/`, `bugs/`, `needs-decisions/`, `decisions/`, `business/`, `frontend/`, `backend/`, `design/`, `Card Index.md`) is inside `social-pin/`: `modules/…` means `social-pin/modules/…`. Wikilinks go by note name and never carry the folder.

## 1 · The layers

The vault is organised by **feature**, and inside a feature by **layer**. A layer is a team or a concern that produces notes: today business, frontend, backend and QA. The layers, their note kinds, their statuses, the hand-off order and the default blocks are declared in **`docs.config.json`**, not in code: adding a layer (DevOps, AI, Security, Design) is a config change plus a template ([[#5 · Adding a layer]]).

| Layer | Writes | Reads first |
|---|---|---|
| **Business** (product: the owner and the PM) | the module note and the feature note (`F-NN <Feature>.md`, the main node) with its business side, by the owner; `S-NN <Feature> Story` (one per feature, holding all of its work) and the feature note's *Decisions* list, by the PM; signs stories and requirements off and decides the decision cards `ND-NN`, which any layer raises ([[#4 · Statuses, blocking and sign-off]]). Agents: [[Owner Agent]], who also writes the rules and the config, and [[PM Agent]] | the module note, the screens in [[Screen Index]], open decisions |
| **Frontend** | `FR-NN <Feature> Frontend Requirements` (what the client asks of the backend, **before** backend work), `FD-NN <Feature> Frontend Delivery` (what the client shipped, **after**), `QF-NN <Feature> QA Frontend` when it runs the checks. Agent: [[Frontend Agent]] | the story, the Backend Integration note, [[Frontend Contract]], [[Frontend API Guide]] |
| **Backend** | `BD-NN <Feature> Backend Delivery` (what shipped, how it works, gaps), `BI-NN <Feature> Backend Integration` (how the client calls it), `QB-NN <Feature> QA Backend` when it runs the checks. Agent: [[Backend Agent]] | the story, the Frontend Requirements, [[Ring Access Model]], [[Architecture]] |
| **QA** | `QB-NN <Feature> QA Backend`, `QF-NN <Feature> QA Frontend`: expected behaviour as tables and diagrams, **never test code**. Agent: [[QA Agent]] | the story, both delivery notes |

The default flow, drawn as dashed arrows on the tree page: Story → Frontend Requirements → Backend Delivery → Backend Integration → Frontend Delivery → QA Frontend, and Backend Delivery → QA Backend; both QA notes feed back into the Story, whose `verified` status means the implementation matches it. **Each hand-off is also a block**: a card is blocked by default until the card before it in the flow is handed off (`approved` for a story or a requirements list, the done status for every other kind), so nobody starts a Backend Delivery before the Frontend Requirements are approved, or a QA Frontend note before the Frontend Delivery is done. A note's own `blockedBy` overrides the default ([[#4 · Statuses, blocking and sign-off]]).

A layer writes **only its own notes**. It reads the others. If a backend change makes a frontend note wrong, the backend does not edit it: it flags it ([[#3 · Relations]]) and the frontend updates it. The agents are declared in `docs.config.json` (`agents.list`: the note that is each one's prompt and the files it may write) and held to that by a hook (`scripts/agent-guard.mjs`); how they take a request is [[Agent Protocol]]. While no agent is active nothing is written: the first answer is the question which agent to use. One agent is no role: [[Admin Agent]] (`/admin`) may write anything, for the repairs and migrations the roles cannot do; the rules in this note still hold for it, unenforced.

## 2 · Codes, scopes and the "sum of" rule

- **One story per feature, one flow.** (Since 2026-10-27.) A feature has **one** user story, `S-NN <Feature> Story`, and every piece of its work lives in it: a new screen, a change, a gap the backend has to fill is a new part of that story (`### S7 · …`) with its acceptance criteria, never a separate ticket. Its work then runs through the feature's **one** flow: Story → Frontend Requirements → Backend Delivery → Backend Integration → Frontend Delivery → QA. There are **no tasks**: no `T-NNN` card, no second story, no layer notes outside the feature. The feature card carries the priority and the deadline; the layer notes carry the status and the `## Log` of what shipped; code branches are named after the feature, `<module>/<F-NN>/<what-you-do>` ([[Workflow#2 · Branch from the feature]]). A note with `type: task` or `scope: task`, a `taskFlow` or `taskLabels` key in the config and `--scaffold task` are build errors; the retired `T-` codes stay retired in `tree/cards.json`.
- **New work on a feature whose notes are already done** reopens them as **Partial**, never as a second card: when the backend approves new requirements on a feature whose Backend Delivery is `done`, it adds one `pending` entry per new ask to that Backend Delivery (`pending: ["[[FR-NN <Feature> Frontend Requirements]]: <the ask>"]`), so it shows 🟡 Partial and the requirements cannot show ✅ Delivered until every entry is built and cleared ([[#4 · Statuses, blocking and sign-off]]). The frontend does the same on its Frontend Delivery for new screens in the story, and QA on its notes for new rows. The notes keep their `done` status and their history; the `pending` list is the open work.

- A **bug** is its own note type, `type: bug` (tags `bug`, `bug/<status>`), created with `node scripts/build-tree.mjs --scaffold bug` from `templates/Bug Template.md`. Its file lives in its own folder, **`bugs/B-NN <Title>.md`** (beside `needs-decisions/` and `decisions/`), whatever card it hangs under; its file name starts with its code, and the build warns on one that does not or on a bug anywhere else. Its id, and so its card code, is **`B-NN`** on its own sequence (`cardCodes.structural.bug`), and it reads `B-01 · BUG` on the page. Its statuses are `todo | needs-info | blocked | in-progress | done`. It takes no story, no layer notes and no labels (`type: bug` says what it is; a `labels:` or `parent:` line on a bug is a build **error**).
- **A bug hangs where it was found, not on the work it belongs to.** A bug names the card it was found against — a QA note, a Backend Integration note, a delivery note, the story — by note name in **`foundOn:`** (required) and hangs under it in the tree: `node scripts/build-tree.mjs --scaffold bug <feature-id> "<Title>" --found-on "<note name>"`; `foundOn` must name a card in the bug's own feature, never another bug. The feature still rolls the bug up wherever it hangs.
- `foundOn` takes the **note name** (`BI-01 Account Backend Integration`, code included since it is part of the name), not the bare card code: card codes are handed out after the tree is built, so they cannot be resolved while it is being built, and the vault links by note name everywhere else ([[#3 · Relations]]). The scaffold writes a `**Found against:** [[<the card>]]` line under the H1 and puts the card in `related:`. The QA note whose row failed is named under it too, with the row (`**Found by:** [[<QA note>]] row BNN`), and the bug goes in that QA note's `pending:` so it stays Partial until the bug is closed.

- A **feature** has an id (`rings`) and one note per layer next to it: `modules/<Module>/features/<Feature>/S-NN <Feature> Story.md`, … (`scope: feature`, `code: <id>`); the feature note itself is `F-NN <Feature>.md` in the same folder, the module note `modules/<Module>/M-NN <Module> Module.md`. The folders carry no code.
- **A module note is the sum of its features**: its table is kept current. Like the feature note, it is a business note: its first paragraph and its *Product rules* say, in product terms, who the people are, what they get done and what holds across every feature; vendors, endpoints and tables stay in the layer notes, and a choice not yet taken is a decision card, not a sentence (`templates/Module Template.md`).

- **Every card has one unique card code, and it never changes.** A card is one Markdown file in the tree (a module, a feature, a layer note, a bug, a decision, a project reference note). Its code is `<prefix>-<number>`: a bug's and a decision's code is its id (`B-01`, `ND-04`, `D-04`); every other card got the next free number for its kind's prefix the first time the build saw it, in tree order (`M-01` module, `F-05` feature, `S-01` story, `FR-05` frontend requirements, `BD-05` backend delivery, `BI-01` backend integration, `FD-01` frontend delivery, `QB-01` QA backend, `QF-01` QA frontend, `P-10` project note; the prefixes are `prefix` per kind and `cardCodes.structural` in `docs.config.json`). The build keeps the codes in `tree/cards.json` and lists them in [[Card Index]], one row per card with the cards it is connected to as `B-01 | S-01` (*Under*, *Related*, *Blocked by*). A new card gets the next number; a deleted card's code moves to `retired` and is never handed out again; a code given twice, renumbered or carrying another kind's prefix is a build **error**. Neither file is edited by hand, with one exception: a card restored under the same id may take its own retired code back by writing it into `cards`. The feature id in frontmatter (`code:`, `feature:`) stays what it is. `--impact S-01` resolves a code; the tree page finds a card by its code.
- **Every card's file name starts with its code** (since 2026-10-28), as a bug's always did: `B-01 An unverified changed email still signs in.md`, `M-07 Commerce Module.md`, `F-27 Payments & Orders.md`, `S-69 Payments & Orders Story.md`, `FR-27 Payments & Orders Frontend Requirements.md`. The code comes first, then the name the card had before (the kind word stays); the folders keep their names without a code. A card is **born with its code**: `--scaffold feature` and `--scaffold <kind> <feature-id>` take the next free number for the prefix and write `<code> <name>.md`, and the build keeps the code the file name gives a new card. A card not written yet (a placeholder in the tree) has no code and is linked by its plain name (`[[Payments & Orders Backend Integration]]`); the scaffold that writes it repoints every such link, bodies and frontmatter lists alike, at the coded name and lists the notes it touched. The build **warns** on a card whose file name lacks its code, or on a link written to the plain name of a card that has one, and fails on a file name whose code is not the card's. Wikilinks go by that full note name, code included ([[#3 · Relations]]). Project reference notes (`P-NN`: the rules, the backend, frontend and business references) keep their plain names: the skills, the config and the guard open them by path.
- **Project docs are not feature docs.** Stack, migrations, conventions, contracts, glossary live in `backend/`, `frontend/`, `business/`, `rules/` and never inside a feature's notes or a bug. A feature note links to them.

## 3 · Relations — the context an agent reads instead of the whole repo

Every note declares what it is connected to, in frontmatter, and the build turns that into a graph you query **before** touching anything.

| Key | Meaning | Direction |
|---|---|---|
| `depends: [...]` | cannot be done until those are done; feeds blocking | one-way |
| `affects: [...]` | changing this changes what those rely on | one-way |
| `related: [...]` | shares a concept, endpoint, table, screen or rule | symmetric (the build mirrors it) |
| `blockedBy: [...]` | what blocks this note right now; `[]` means "nothing, whatever the defaults say" | one-way |

A target is a note name (`"Ring Access Engine"`), a bug or decision id (`B-01`, `ND-04`), a feature or module id (`rings`, `identity`), a **kind id** meaning the sibling note of that kind in the same feature (`backend-integration`), or a **concept**: an endpoint (`"GET /rings/:id"`), an error code (`E_RING_02`) or a screen (`s14`). A concept expands to every note that mentions it. The build also derives `shares` links between features that mention the same endpoint or error code, and knows which feature **owns** an endpoint (the Backend Delivery that lists it).

**The rules:**

1. **Before** creating or changing a card, run `node scripts/build-tree.mjs --impact "<note name | card code | feature id | concept>"` (or read the node's edges in `tree/tree.json`). Read what it returns, in this order: the same feature's notes, the directly linked notes, the two-hop notes only when the change crosses a feature boundary. Do not read the rest of the vault.
2. **Every note you create or change declares** `depends`, `affects` and `related` to what it touches: the features, cards and decisions, the endpoints it calls, the error codes it handles, the screens it serves. An endpoint owned by another feature without a declared relation is a build warning; fix the frontmatter, do not ignore it.
3. **After** a change that alters an endpoint, an error code, an access rule or a screen, run `--impact` again and **update or flag every note it lists** that you do not own: add a line `> ⚠ Affected by [[<the card you changed>]] (YYYY-MM-DD): <what changed>` under the note's H1. The owning layer removes the flag when it has updated the note. Name the flagged notes in the `## Log` of the note you changed.
4. A relation lives in the frontmatter key. A sentence in the body or a wikilink is not a relation the graph can act on (wikilinks are drawn as *mentions* only).
5. An unresolved target is a build **error**; a `depends` on something already done is harmless.

## 4 · Statuses, blocking and sign-off

- Each kind's statuses and its *done* set are in `docs.config.json`: story `draft → approved → verified` (shown as 👍 Approved and ✅ Fulfilled; only `verified` is done); frontend-requirements `draft → ready → approved → delivered` (📨 `ready`: the frontend finished the list and waits for the backend; it hands nothing off, so the backend cards stay blocked until `approved`; the backend sets `approved`, or sends it back to `draft` with what is missing written in the note; `delivered`, ✅, is computed by the build once the Backend Delivery and Backend Integration of the same scope are done with nothing pending; nobody types it, except on a `frontendOnly` feature); backend-delivery and frontend-delivery `todo → in-progress → done`; backend-integration `draft → current → delivered` (✏️ Draft, 🔵 Current: matches `main`, handed off, in use but not done; ✅ Delivered: computed by the build once, in its scope, the QA Backend is passing and the Frontend Delivery done, both with nothing pending; nobody types it, the file stays `current`, and a note set back to `draft` when the API moves loses it); qa-backend and qa-frontend `draft → passing | failing`. Structural: bug `todo | needs-info | blocked | in-progress | done`, needs-decision card `draft | open` (shown ✅ Fulfilled, computed, once its decision card is decided), decision card `draft | decided`. A story and a requirements list also have a *handoff* set (`approved`): the next card may start from there, before they are done.
- **A feature, a module and the project have no status of their own; the build computes it from the cards.** A feature is **Done** only when every card under it is done: every layer note (a card that is not written yet counts as not done), every bug hanging under them, every decision. It is **Partial** when every card is done or partial, **In progress** when any card is in progress or the cards are a mix of done and not done, **Blocked** when every card waits on something, **To do** otherwise. One thing overrides the rollup: a decision raised on the feature itself (`blocks: [<feature id>]`) makes the feature **Blocked · ND-NN** while it is open, whatever its cards short of done, exactly as it does a layer note; the feature returns to its computed status on the build after the decision is `decided`. A module rolls up its features the same way, the project its modules. Never type a feature's status: the feature note has no `status:`, no `status/*` tag and no status emoji in its H1; its body may state what the backend shipped (`**Backend:** Done`). A feature with no backend part carries `frontendOnly: true`, which drops the backend and QA-backend cards from its requirements and its rollup.
- **Partial means done with notes left.** A layer note or a bug whose own status is done and that carries a `pending` list is Partial until the list is cleared: `pending: ["[[FR-11 Rings Frontend Requirements]]: confirm the page size", "@product: approve the copy"]`, one entry per note, addressed to a card (`[[<Note name>]]`, which must resolve) or a person (`@name`). The tree draws a *pending* line to the card, the chip reads *Partial · 2 notes*, the pane lists the notes. Clear your own entries when they are answered, or hand them over as a flag or a part of the story; a Partial card still blocks the next card in the flow.
- **A bug says how it ended, in `resolution:`.** A bug (`type: bug`) takes the bug statuses and nothing else: `status:` says where the card stands and never how the bug turned out. The outcome is its own key, on the bug card only: `resolution:` — one of `resolutions.levels` in `docs.config.json`, `fixed` (the behaviour changed, code shipped), `by-design` (the build was right and the expectation was wrong; the words moved instead), `duplicate` (another card covers it, named in `related`), `cannot-reproduce` (not seen again on a named build) or `wont-fix` (real, accepted, not scheduled; the gap stays written down) — mirrored by the tag `resolution/<id>`. It is **not** required and it is never inherited: a card that is not a bug carrying the key is a build **error**, an unknown value is an **error**, and a bug at `status: done` without one is a **warning**, because a closed bug that does not say how it ended tells the next reader nothing. `by-design` and `wont-fix` are product calls: name the decision card they rest on in `related` ([[#4 · Statuses, blocking and sign-off]] above), since neither is the kind of answer an agent takes alone. `resolution` changes nothing about the status rules: a bug at `done` with a `pending` list is still **Partial** whatever it resolves to, and a bug that is still open carries no resolution. **It is reserved for the PM and QA**, who are the agents that write bug cards — QA files them, the PM closes them — and `agents.reservedFields` lists it, so the guard refuses the line from any other agent. The tree draws it beside the status.
- **Status transitions are part of the work.** Every agent moves its own cards' statuses when the event happens, in the same commit as the work, without being asked, and names what moved in its report; each agent note lists its own moves in a *Status transitions* table ([[Backend Agent#4F · Status transitions: yours, unasked]], [[Frontend Agent#4E · Status transitions: yours, unasked]], [[QA Agent#4F · Status transitions: yours, unasked]], [[PM Agent#5 · Sign-off and status changes]]). Sign-offs (approving a story or a requirements list as the PM or the owner, deciding, closing a bug, fulfilling a story) still wait for the user's word; the agent proposes them the moment they are due. The build reports what was left behind, so nobody has to remember it: a Backend Delivery `in-progress` whose Backend Integration is `current` or whose `## Log` records a merge to `main` (**warning**: set it `done`); a `done` Backend Delivery with no `current` Backend Integration in its scope (**warning**: the requirements can never show ✅ Delivered); a Frontend Requirements list `ready` for `staleness.readyDays` (3) days or more since its `updated:` and not reviewed (printed as **`stale`** on every build: it depends on today's date, so, like a deadline's zone, it is never written into a generated file).
- **Priority and deadline.** Every card may carry `priority:` (one of `priorities.levels` in `docs.config.json`: `critical`, `high`, `medium`, `low`, highest first; the tag `priority/<id>` mirrors it; the old `P0`–`P3` are aliases the build normalises with a warning, so write the new ids) and `deadline: YYYY-MM-DD`. Neither is required; both are **inherited down the tree** when absent: a layer note and a bug take their feature's (`inherits` on the node names the source). An unknown priority or a malformed date is a build **error**. The tree draws a flag in the priority's colour and a clock in the deadline's zone colour: the window (`deadlines.windowDays`, 3 days) before the deadline is split evenly over `deadlines.zones`, farthest first, so with three zones the card is *on track* (green) until two days before, *due soon* (yellow) the day before, *last day* (red) on the deadline day and *missed* (💀) from the next day; the zone is computed when the page is viewed (and by `--impact`), never written into a generated file. Changing either is a frontmatter edit plus `updated:`; there is no emoji for them in the H1.
- **Stage, release and environments: where the product is, not how far the work got.** The project's **stage** is typed by the owner, and only the owner, as `stage:` in [[Project Overview]] (the tag `stage/<id>` mirrors it): one of `stages.levels` in `docs.config.json`, `concept` → `prototype` → `mvp` → `beta` → `live` → `sunset`, each with the `exit` test that moves it to the next one. It is never computed and never replaces the project's computed status. A missing stage is a build warning, an unknown one an error; a stage with `requiresRelease` (`beta`, `live`: `mvp`) is a warning while any feature of that release is not Done. A feature's **release** is `release: mvp | v1 | later` on the feature card only (`releases.targets`; the tag `release/<id>`), set by the owner; its layer notes and bugs inherit it (`inherits.release`), and a `release:` on any other card is an error. The project card counts, per release, the features Done out of the total. A delivery's **environments** are `deployedTo: [dev, staging, prod]` on the kinds `environments.kinds` names (Backend Delivery, Frontend Delivery), written by the layer that owns the note when it deploys; an unknown environment, or `deployedTo` on another kind, is an error. An environment is never a stage: the project can be at `mvp` and run on all three. **`release:` and `stage:` are reserved for the owner**, on the user's word: `agents.reservedFields` in `docs.config.json` lists them, and the guard refuses any edit or rewrite that adds, changes or removes either line from another agent (the admin excepted), even on a note that agent otherwise writes (the PM keeps the feature card's *Decisions*, never its release). How the page draws them: [[Docs Tree#Stage, release and environments]].
- **A card that needs a decision gets a decision card, and is Blocked until it is decided.** (Two cards, two prefixes, one number: the **needs-decision card** `ND-NN` holds the question and always reads `ND-NN · NEEDS DECISION`, its kind, with a chip saying Draft, Open or Fulfilled; the **decision card** `D-NN` holds the answer and reads `D-NN · DECISION`, with a chip saying Draft or Decided.) Any layer note or feature can need a decision before it can continue. **Whoever owns the card raises the decision card, whatever their layer** (every agent may write `needs-decisions/`): `node scripts/build-tree.mjs --scaffold needs-decision "<card>" "<title>"` writes `needs-decisions/ND-NN <Title>.md` from `templates/Needs Decision Template.md` with the next free `ND-NN` (never a retired one), `status: draft` (set to `open` once the question is ready for the decider; both block), `blocks: ["<card>"]` (the card that needs it, by note name or feature id; more cards can be added) and `features:` derived from it. The decision card says **what has to be decided**, the **notes** (facts, constraints, options) and who is **responsible** (`decider:` plus the *Responsible* section). The build then hangs the decision **under the card that needs it** (a child in the tree, `decision` edge, listed in the card's *Under* / *Related* in [[Card Index]]) and marks that card **Blocked · ND-NN** (reason: *needs decision ND-NN*), whatever its own status short of done; the cards below it in the ladder wait in turn, and the tree shows the decision as the reason. **Nobody edits the blocked card's `status:` for this**: it keeps `todo` / `draft` / `in-progress`, the chip is computed. **Only the PM or the owner decide it, and only on the decision card.** The needs-decision card is never typed `decided` or `fulfilled` and carries no `decidedBy` / `decidedAt`: the guard refuses it from anyone, the build fails on it. **The answer goes on its own card, the decision card `D-NN`.** `node scripts/build-tree.mjs --scaffold decision ND-NN "<the answer>"` writes `decisions/D-NN <the answer>.md` from `templates/Decision Template.md` (`type: decision`, the question's own number, `decision: ND-NN`, `status: draft`): *What was decided* (the option, in the product's words, and what it rules out), *Why* (the facts that weighed, who was heard, what was traded away), *What it changes* (every feature and card it changes, also listed in its `affects`) and *Still open*. It may sit in `draft` while the answer is prepared; nothing is released. On the user's word, in that message, the PM or the owner sets it `decided` with `decidedBy` and `decidedAt` (the tag `decision/decided`); only they write decision cards (`decision` in their `types`). **The needs-decision card then shows ✅ Fulfilled by itself** (computed by the build, never typed); its H1 gets ✅ and its *Decision* section is reduced to one line pointing at the decision card; the answer is never written into it, it keeps the question, the facts and the options. The build fails on two decision cards for one question, and on a decided answer to a question still in `draft`. When the user raises and decides in one message, the PM or the owner scaffolds both cards in the same step. On the next build the card **returns to its own status** (To do, Draft, In progress) and continues normally; the decision stays under it, with its record under the decision. A card may point the other way too (`blockedBy: [ND-NN]` or `depends: [ND-NN]` on the card) with the same effect; `blocks` on the decision is the canonical direction because the decision card is created after the card that needs it. A decision raised only in prose, or a card typed `blocked` by hand for a decision, does not count.
- **Sign-off** is a status change plus `approvedBy` / `approvedAt` on the note: product approves a story; the backend approves a requirements list once the frontend has set it `ready`; a Backend Integration note is `current` when it matches `main`; QA sets `passing` or `failing`; a story is **fulfilled** (`status: verified`, ✅) by the **PM** (or the owner) on the user's word, and only once every QA note of its scope is `passing` with nothing left in `pending`: QA finishes its job, the PM fulfils the story. The build refuses a story fulfilled earlier (`--check` error). An `approved` story is handed off, not done: its feature is not done until it is fulfilled. A decision that a part of the story needs blocks the story (`blocks: ["S-NN <Feature> Story"]`), so the story and the cards after it show **Blocked · ND-NN** until it is decided.
- **Blocking follows the flow by default and is symmetric across layers.** Every forward pair in the config's `flow` is a block: the card is blocked until the card before it is handed off (Frontend Requirements by the Story, Backend Delivery by the Frontend Requirements, Backend Integration and QA Backend by the Backend Delivery, Frontend Delivery by the Backend Integration, QA Frontend by the Frontend Delivery). `defaultBlocks` in the config adds blocks outside the flow (a DevOps or design kind). A note overrides all of that with its own `blockedBy` list, in either direction: a frontend note may be blocked by a DevOps note, a backend note by a design decision, or nothing at all (`blockedBy: []`). A bug is blocked by anything in its `depends` or `blockedBy` that is not done. The tree shows *Blocked* with the reason.
- Changing a status on a card (a layer note, a bug, a decision) means: `status:` in the frontmatter, the tag (`<kind>/<status>`), the emoji in the H1, `updated:`, then a rebuild. A feature's and a module's chip change on their own.

## 5 · Adding a layer

1. In `docs.config.json`, add a `layers[]` entry: `id`, `label`, `color`, and its `kinds[]`, each with `id`, `label`, `file` (the note-name suffix, e.g. `DevOps Delivery`), `statuses`, `done`, `template`, `description`.
2. Add the template under `templates/` (copy the closest existing one; the frontmatter keys are the same for every kind).
3. Insert the kind into `flow` where it hands off (for example `["backend-integration","devops-delivery"]`, `["devops-delivery","frontend-delivery"]`) and add `defaultBlocks` if other kinds should wait for it by default.
4. Add it to `requiredAtFeatureLevel` only if every feature must have one; otherwise it appears where it is scaffolded ([[Docs Tree#The shape]]).
5. `node scripts/build-tree.mjs --scaffold <kind> <feature-id>` creates the notes; `node scripts/build-tree.mjs` rebuilds. The page's filter, legend, colours and flow arrows follow the config with no code change.

## 6 · After a change — the checklist, by layer

**Everyone**: `--impact` before and after; relations declared; flags placed; your `pending` entries cleared or handed over (a Partial card is not done); no card started while the card before it in the flow is not handed off, unless its `blockedBy` says otherwise; every card keeps the `created:` it was made with (written once by the scaffold or the template, never changed) and every touched note gets today's `updated:`; `node scripts/build-tree.mjs` run and `tree/` and `Card Index.md` committed with the notes (they are generated; `--check` fails on drift). The branch in every code repository is `<module>/<F-NN>/<what-you-do>`; pull requests link each other and the feature. In the vault every agent's branch is named after the card, `tickets/<agent>/…` for the cards that ask for or plan work (story, Frontend Requirements, needs-decision card, bug) and `docs/<agent>/…` for the archive of what is (delivery, integration and QA notes, decision cards, module and feature cards, the rules), as `node scripts/build-tree.mjs --branch` prints it ([[Workflow#2 · Branch from the feature]]).

**Business**: the story's new part with its acceptance criteria, its status and sign-offs; a needs-decision card (`--scaffold needs-decision`) for every card that needs one, with what has to be decided and who decides, and, when taken, its decision card (`--scaffold decision ND-NN`, with `affects` listing what it changes) and the decision's `decided` sign-off; the feature note's *Decisions* list; the module note when a feature is added.

**Frontend**: `FR-NN <Feature> Frontend Requirements` before asking for backend work (rows ✅ / ❌ with the endpoint or the story part); after shipping, `FD-NN <Feature> Frontend Delivery`; [[Frontend Contract]] when the client's cross-cutting rules changed.

**Backend**: `BD-NN <Feature> Backend Delivery` (what shipped, how it works) and `BI-NN <Feature> Backend Integration` (how to call it); the module table's *Backend* column when what shipped changed (the feature's chip is computed, never typed); `backend/` reference notes ([[Spec Map]], [[Developer Guide]], [[API Conventions]], [[Database & Migrations]]) when the stack, a migration or a convention changed; [[Frontend API Guide]] and the Frontend Requirements rows (✅ with the endpoint) when the contract moved.

**QA**: the QA note's table rows checked, the diagram current, `status: passing | failing` with the run date and build; when both sides pass with nothing pending, the story is reported ready to fulfil (the PM sets it, never QA).

## 7 · What never happens

- A relation added only in prose. A status changed only in the H1. A hand-edited `tree/tree.json`, `tree/tree.md`, `tree/cards.json` or `Card Index.md`.
- A layer editing another layer's note instead of flagging it.
- Feature behaviour written into a project reference note, or stack / migration detail written into a feature note.
- A feature or module status typed by hand: the chip is computed from the cards, and a feature is not done while any card under it is not.
- A card marked done while the card before it in the flow is not handed off, without an explicit `blockedBy` saying why that is fine.
- A card that needs a decision without a decision card under it (`--scaffold needs-decision`), a decision raised only in prose, or a card's `status:` typed `blocked` by hand because of a decision: the decision card blocks it and releases it, the build computes the chip.
- A `pending` note left behind: it is cleared by its author, or handed over as a flag or a part of the story.
- A second copy of a rule: the vault has one place for each (this note for rules, [[Workflow]] for the sequence, [[Docs Tree]] for the page and the JSON).
